# Reviewed local leaf materialization

Draft contract: `LocalLeafMaterializeV1`. Native Linux qualification is required before this candidate is admitted as a supported installer. This workflow writes reviewed archive data. It never launches Node, npm, lifecycle scripts, a resolver, an archive utility, or any other package-controlled process. The existing package execution gate remains closed.

The core accepts one through eight exact local leaf tarballs, validates the complete retained compressed archive before obtaining output authority, and refuses unsupported scripts, execution declarations, dependency graphs, native payloads, metadata, archive ambiguity, or incomplete bounded analysis. Ordinary JavaScript and other supported files remain inert data. Output uses fixed nonexecutable file permissions and private directory permissions. Native addons, bin links, dependency solving, and npm runtime compatibility are not supplied by this contract.

## Review and apply

`tirith pkg materialize plan ARCHIVE... --target NEW_DIRECTORY --json` inspects the complete local selection, captures current effective policy and signed threat data, obtains the exact local task authorization, and records an immutable private intent. The response includes `operation` and `reviewed_sha256`. It contains no private policy replay digest or native recovery inventory.

After reviewing that output, invoke `tirith pkg materialize apply OPERATION --reviewed SHA256 --json`. Apply runs in the original working directory. It reopens every archive without following the final symlink, checks the original native file generation and bytes, recaptures current complete policy and threat data, rebuilds the exact plan, and requires the reviewed public and private commitments to match. The current live plan instance supplies a fresh typed task permit. A saved JSON record or matching digest does not construct that permit.

Remote policy configuration refuses before a request is made. This uses the complete runtime policy resolver, including its list, trust, incident and label inputs, within a narrow remote-refusal scope. Local-only diagnostic policy is never promoted to mutation authority. Signed threat database build age is a bounded publication-age proxy, not a claim that an upstream service or fleet is current.

The target must be absent under a canonical parent owned by the current user and protected against writes by other users, including ACL grants. The parent ancestry is checked and retained through the operation. The native writer populates a private fixed `.tirith-materialize-OPERATION/pending-target` tree. Publication verifies its complete held inventory, durably records a private recovery milestone, permanently disables private cleanup, and performs an atomic no-replace rename. The final verified observation is produced from the live core writer only after rehashing the public target.

## Interruption and recovery

The state root contains bounded immutable intent, start, completion, and explicit confirmation/undo attempt records. A start is written before creating the package checkpoint; another apply cannot replay an already started operation. Neither ordinary process exit nor `Drop` recursively removes files. A live prepublication error may clean only the core writer's exact retained inventory; changed or unrecognized objects are preserved.

Explicit `status`, `recover`, `undo`, and `continue-undo` are distinct from apply. Status reports historical phases and whether the fixed public/private names are absent, present, or unavailable. Presence is not evidence that an installed generation remains unchanged or safe. Status never grants execution authority.

`tirith pkg materialize undo OPERATION --reviewed SHA256 --json` withdraws an unstarted intent using only its locked history. Withdrawal remains possible if an archive is lost, its malware classification changes, or installation policy no longer permits it. Once the durable start record exists, undo uses the native recovery checks below instead.

Recovery uses a complete durable inventory milestone as expected evidence. It reacquires the fixed journal lock and current native handles, then requires fresh task authorization and checks every recorded object identity, expected byte hash, permission, and complete entry set. It does not regain the original process's ownership lease. Confirming public output requires current artifact Allow and complete current policy; undo of an unchanged recorded tree requires current delete authorization and does not require a positive installation verdict for newly malicious bytes. A public undo first relocates the exact verified root into the fixed private pending name with a no-replace rename under that same deletion lease. It then removes only the verified contents, retaining the empty root and journal. Package payload is never replayed during recovery.

After interrupted deletion, invoke `tirith pkg materialize continue-undo OPERATION --reviewed SHA256 --json` explicitly. It requires an original complete recorded milestone, the original archive inputs, the original working directory, an actual private pending tree, and fresh current deletion authorization. It does not move a public tree or select continuation automatically when ordinary undo fails. Core reopens the remaining inventory, checks present file identities, bytes and permissions, and rejects replaced directories, links, modified files and extra names. Changes to directory generations from removed children are captured as new observations.

Continuation reports `recorded_entries`, `remaining_entries_at_capture`, and `missing_recorded_entries`. Missing entries describe current absence; they do not prove that an earlier undo deleted them. A continuation that removes remaining entries records `private_contents_continued_undo_empty_root_retained`. If it finds the private tree already empty, it records `private_tree_observed_already_empty_root_retained` and claims no deletion. Status reports an attempt without a completion as `continue_undo_incomplete_or_running`, ahead of older undo history. Both completed phases are historical observations. An interrupted continuation can be explicitly requested again with fresh capture and authorization; after a completion is durably recorded, use status rather than repeating effects.

A crash before a complete inventory milestone, unrecorded partial writes, changed objects, conflicting generations, or extra entries remain reported and preserved. Ordinary undo and confirmation retain their complete-inventory requirements; only explicit continuation accepts missing recorded entries. A recorded private/public transition permits only the expected root ctime change with its identity, other native fields, complete inventory and bytes verified by core. These are newly observed generations under fresh authorization, not proof of continuous ownership through a crash. Native recovery evidence is part of qualification, not inferred from the presence of a journal. Private checkpoint metadata and harmless empty roots can remain as explicit recovery history.

## Bounds and authority limits

Global immutable records are individually capped at 64 KiB, with at most 1,024 fixed-name records in one state root; capacity refusal preserves existing history. A checkpoint has at most 12 entries and two complete inventory milestones capped at 2 MiB each. Core payload paths and retained native objects have their own smaller fixed admission limits. These are retained-input/object bounds, not a claim of universal process memory or latency limits.

The state directory and checkpoint are operator-owned and private, and file reads use retained no-follow ordinary descriptors. Native descriptor comparisons and final hashes identify the generations actually inspected. They are not a lock against an arbitrary other process owned by the same user between checks or after publication. No published bytes, same-UID edit, serialized report, or historical success becomes authorized execution. `package_code_executed`, `execution_authority`, and ongoing immutability remain false; code safety is not established by materialization.
