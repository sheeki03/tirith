# Stored automatic setup observations

A completed automatic activation attempt can retain a bounded historical terminal observation for its exact recommended setup operation and claim. This is ordinary operator-owned private storage, not persistent cryptographic attestation. It cannot authorize execution, establish current protection, or replace the live native shell, setup lease, authenticated transport, and core proof required by the automatic coordinator.

The coordinator spends the claim as `Ended` before publishing the terminal result. The result records the channel, client version, original completion identity, exact attempt and claim bindings, and one closed outcome: `observed_blocking`, `cancelled`, or `refused`. An observed blocking result is accepted only from the matching core automatic observation after restoration. The private record contains no reusable hook capability or signing key. A different existing result cannot be overwritten; an identical publication may be recognized without changing it. A failed publication never yields the normal successful finish response, even if the core observation was consumed. The completed setup lease remains held through the existing final reply handshake.

The record does not assert that the terminal received that reply. A process exit, deadline, lost ownership, or failed publication can leave `Pending`, `Running`, or `Ended` without a result. In particular, a saved `Running` phase cannot distinguish a still-running attempt from an interrupted one and is never displayed as live verification.

`OperationStatus` and the dashboard's saved-operation views add an optional `setup_activation` projection. The existing journal and claim formats remain schema 1. Older records with no result produce `missing`; a claim without a result produces `incomplete`; malformed, unsafe, oversized, or mismatched private records produce `invalid`; a matched result produces `recorded`. Mutation responses that have not loaded history may omit the optional field; refresh stored status to retrieve it. None of these values changes `current_protection`, which is always `unknown` in this projection.

A recorded result retains its original observation and expiry times even after expiry, undo, or edits. These times describe the former observation; they do not grant freshness. An explicit saved-status read separately compares at most 16 recorded setup documents with one shared 8 MiB content budget. It reports `recorded_inputs_match`, `changed`, or `unknown`; this comparison does not inspect the current shell, executable, effective policy, or arbitrary dynamic startup inputs. Undo or invalidation reports setup changed while retaining the historical observation. The recent-jobs inventory reads only the private result and claim, at most 4 KiB each per retained row, and marks current document comparisons `not_checked`.

Storage uses the existing scoped no-follow private-file reader and contained transaction machinery in `automatic-activation-outcomes/<operation-id>.json`. It binds the original journal, operator/state scope, client, channel and exact ended claim. Public output omits storage and input hashes, native process identities, loaded-state fingerprints, capabilities, and private paths. Like the other private journals, these records assume the operator's private storage has not been wholly rewritten by that same operator; the dashboard does not claim a durable signature against such rewriting.

The fixtures cover private-record integrity, bounded input, immutable publication, scope and claim mismatches, malformed core reports, missing older records, and history after actual setup undo. Those fixtures do not qualify an interactive automatic activation or attest that any shell remains protected. Actual shell and transport qualification remains a separate requirement.
